# Admin Portal

The dashboard prototype is available at `/admin`. Its component and isolated styles live in `AdminPortal.tsx` and `admin.css`; the route is selected in `../main.tsx`.

Dashboard figures and notifications are demonstration data. Backend authentication and role-based authorization are required before connecting real administration features or exposing sensitive data. The current route is not an access-control mechanism.

The shared admin sidebar connects Overview, Bookings Management, Tours & Experiences, Guides Management, Customers Management, Availability & Scheduling, Payments Management, USSD Activity, Reports & Analytics, Website Content, Settings and Activity Logs; Booking Details and Guide Assignment open from individual reservations. Booking, guide, tour, website content and settings changes use sample records only; changes are shared between the admin screens for the current session and are lost on reload.

The Overview calendar and upcoming tours reflect the sample booking records. Platform-wide totals and other operational figures are illustrative and are not calculated from that sample.

Use the calendar month controls to browse dates. Selecting a date opens Bookings Management with the experience-date filter applied, including dates with no reservations. Clear filters to return to all sample bookings.

Bookings Management supports status, search, tour, source, payment, and experience-date filters; CSV export includes only the filtered reservations and each reservation's assigned guide. Pending bookings can be confirmed, and pending or confirmed bookings can be cancelled.

**View Booking** opens Booking Details with customer, experience, payment, source, and guide information plus a demonstration timeline; payment status is tracked separately from booking status. **Assign Guide** opens the Guide Assignment screen, where each booking has at most one primary guide selected from the demonstration guide records in `guides.ts`. Assignment, replacement, and removal require explicit confirmation, only approved guides are assignable, and completed, cancelled, or rejected bookings are locked.

Tours & Experiences supports searching, filtering, creating, editing, publishing, and unpublishing demo tours. A Draft has never been published; Published and Unpublished reflect the current demo catalogue state. Tour names must be unique ignoring case and surrounding whitespace. Renames update matching admin booking and guide tour names without changing historical booking amounts. Selected published tours use the same catalogue in the in-session public website preview; the separate customer catalogue is not updated. Reload restores the initial data.

Guides Management offers a searchable directory and profile details, including tour specialities and pending or confirmed booking assignments. Pending guides can be approved or rejected, approved guides suspended, and suspended guides reactivated; each action requires confirmation. Only approved guides can receive new assignments, while existing assignments are retained and show their guide's current status. Verification documents and pre-session activity history are not supported. Guide changes are frontend demo state, reset on reload, and do not update the separate guide portal.

Customers Management derives its directory and booking history directly from the shared admin demo bookings. It groups bookings only when both the trimmed, case-insensitive name and a phone number of at least ten digits match; records with insufficient identity information are kept separate, and bookings without a name or phone cannot be identified as customers. Shared phones and name variations can still make this heuristic imperfect. Website customers have at least one website booking; USSD-only customers have only USSD bookings. These are booking-channel categories, not proof of account ownership. The admin data has no customer IDs, email addresses, account records, or booking creation dates, so these are not invented. The separate customer portal is an independent demo and is not an authoritative admin account source. Changes to admin bookings appear in customer histories during the session and reset on reload. Other unfinished modules remain future-feature placeholders.

Availability & Scheduling uses those same shared bookings and guides. The booking `date` is the experience date, not the creation date. Its calendar marks pending and confirmed bookings, while the list also retains completed, cancelled and rejected records with their statuses. Today and date filters use the browser's local date; upcoming excludes today. A selected calendar date also filters the list, and monthly navigation and date filters do not modify records. Summary figures count booking records rather than distinct departures. Potential issues count pending or confirmed bookings assigned to the same known guide on the same date; this does not establish a conflict, since times and guide working hours are unavailable. Unassigned and missing guide references are identified separately. Guide availability, capacity and time-based conflicts are unknown. Existing booking, guide and assignment screens handle actions; schedule state and demo changes are reset on reload.

Payments Management reads the same shared admin bookings, one row per booking, and supports search, payment-status filters, a details panel, filtered CSV export, and navigation to Booking Details. The export quotes fields, escapes quotes, and prefixes spreadsheet-formula-like text with an apostrophe. Payment and booking statuses remain independent; Unpaid is supported even though the initial sample contains no unpaid bookings. Payment information is read-only.

The overview sums full booking amounts across all bookings and separately by their current payment status; the failed figure counts bookings, and the record count means bookings with a recorded payment status, not transaction records. Paid and Refunded values are booking values labelled with those statuses, **not** verified money received, retained revenue, or actual amounts refunded. The model stores no transaction IDs, methods, provider references, payment timestamps, received amounts, or refund details, and the experience date is not a payment date. Missing transaction information is shown as not recorded. No payment or refund is processed; verification and refund processing require future backend and payment-provider integration. All records and filter state are temporary prototype state and reset on reload.

USSD Activity reads shared demo bookings whose `source` is `USSD`, not a separate customer or session database. Its summary and payment breakdown count all USSD booking records by their current independent statuses; booking value is the sum of their recorded amounts, including cancelled and rejected bookings, not verified revenue. Search, booking-status and payment-status filters combine for the table and CSV export. The CSV quotes fields, escapes quotes and prefixes formula-like text (including phone numbers beginning with `+`) with an apostrophe to protect spreadsheet users. Details show the current shared guide assignment and link to Booking Details; changes made there are reflected during the session. Demo records and view state reset on reload.

No gateway sessions, menu selections, request or response logs, session timestamps, or payment-provider transaction references are connected or stored. The displayed date is the experience date, not a session or booking creation date. This screen does not monitor live traffic or process USSD requests. Real session monitoring requires a future backend integrated with a USSD gateway.

Reports & Analytics derives its figures from the shared demo bookings, tour catalogue and guide directory. Experience Date filters are inclusive and combine with booking status, payment status and source filters; they affect every booking-derived count, value, chart, customer group, tour count and assignment count. Missing or unrecognized sources appear as Unknown/Other. The summary counts booking records by their current statuses and source; Recorded Booking Value sums their stored amounts across all statuses, including cancelled and rejected records. It is not revenue, actual money received or refunded. Breakdown percentages use the filtered booking count as their denominator and are zero when no bookings match. Payment status is not a settlement report, and USSD booking counts do not measure gateway traffic.

Tour performance uses exact booking experience-name matches against the current catalogue. Unmatched or ambiguous names appear separately with no invented category or publication status; catalogue tours with no matching bookings remain visible. Booking values are historical record amounts, not current catalogue prices. Guide status totals describe the full current directory and do not change with booking filters; assigned and unassigned counts use filtered bookings of all statuses, including assignments to suspended or rejected guides. An assigned reference with no matching guide is counted separately and remains assigned, not unassigned. Assignment is not proof of completion or availability.

Customer patterns use the existing booking-derived name-and-phone grouping heuristic, not verified identities, accounts or retention. Records with neither name nor phone are counted separately; incomplete details remain separate and shared phones or name variations can affect groups. Export includes only filtered booking records, with recorded fields and current assigned guide names where available; the shared CSV utility quotes fields, escapes quotes and prefixes spreadsheet-formula-like text (including `+` phone numbers) with an apostrophe. An invalid date range is flagged and cannot be exported; an empty selection produces a header-only CSV. Experience dates are not booking creation dates; transaction, settlement, session, traffic and guide working-hours data are unavailable. Demo state and report filters reset on reload.

Website Content manages the existing homepage hero heading and emphasis, description, two action labels, image, About heading and description, and featured experience visibility and ordering. The action destinations remain the existing experience and offline sections. Required text and the local-image allowlist are validated. Cancel discards the draft, and navigation warns about unsaved changes. Save updates temporary in-memory content; select **Preview public website** to open the actual public component with those saved values and the current Admin tour catalogue, and return using the preview banner. The same shared content model supplies default values to the normal public page.

Select up to three published tours by ID; order controls determine their placement. Only currently published selections appear, including after a tour is unpublished; a removed catalogue selection is flagged in the editor and can be removed before saving. Unpublishing does not delete booking history. Tour descriptions, prices and images come from the Admin tour record, not a second CMS catalogue. The existing illustrative USSD codes and walkthrough are not a connected gateway and do not update dynamically for catalogue edits. Hero images use the existing local photographs; no upload storage exists.

These are not published changes: preview state is confined to the mounted Admin session, normal reloads and separate tabs restore defaults, and other visitors do not see edits. Contact, footer, informational and USSD sections outside the listed fields are not editable. Real publication, storage, authorization, image uploads and cross-user synchronization require a backend.

Settings shows read-only platform, currency, local-date and system information and links to Website Content for the supported homepage text. Branding, contact information, currency and timezone are not independently configurable. There are no live booking intake services to enable or disable and no real guest-limit configuration.

The optional **Require a guide before confirming** preference defaults off. When enabled, both Bookings Management and Booking Details block confirmation unless the booking references an existing guide record. Existing assignments to guides who are no longer approved still count; only approved guides can receive new assignments. Saving a changed requirement requires confirmation and never alters existing bookings. This is a frontend demonstration, not authorization or backend business-rule enforcement.

Notification preferences control visibility of the existing sample Admin notifications and booking-related sample item, including the displayed count. They do not control real events or send or suppress email, SMS or push notifications. There is no delivery service. Settings edits are drafts until saved; Cancel discards them, and leaving with unsaved edits prompts for confirmation. Saved settings remain in the mounted Admin session and reset on reload. Light/dark selection uses the existing shared theme provider, applies immediately and persists in browser storage when available; Settings Save and Cancel do not affect it. Backend configuration, persistent cross-user settings and enforcement require future implementation.

Activity Logs begins empty; it does not infer events or timestamps from initial records. Successful booking confirmation and cancellation, guide assignment, replacement and removal, tour creation, edits and publication changes, guide status changes, and saved changes to Website Content and demo Settings create session entries. A tour save that both edits and changes publication status creates one entry. No-op saves, failed validation, cancelled actions, navigation, filters and theme toggles do not create entries. There is currently no booking rejection action to record. Customers, scheduling, payments, USSD and reports are read-only views, though actions reached through their existing booking or guide links are recorded by those workflows.

Summary counts use the entire session history: booking-related entries are Bookings; content and catalogue entries are Tours & Experiences and Website Content; administrative entries are Guides and Settings. Search matches action, actor, module or reference; module and type filters combine with search, and sort order applies to the list and export. Details show only recorded information. Filtered CSV includes headers and UTC timestamps, uses the shared CSV escaping and spreadsheet-formula protection, and produces a header-only file for an empty selection. On screen, timestamps use the browser's local timezone. The actor is the unauthenticated label `Admin (demo)`; no contact data or content text is copied into entries. History is kept only in the mounted Admin session and resets on reload. It is not complete, tamper-proof, authenticated or a substitute for persistent server-side audit logging.
